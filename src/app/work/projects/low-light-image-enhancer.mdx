## What I Built

A production-style web app that improves low-light photos using a deep learning model behind an API.

- **Frontend**: upload → preview → enhanced result → download
- **Backend**: Flask inference API wrapping a PyTorch model
- **Focus**: reliable results, predictable latency, and a clean integration path (not chasing paper metrics)

## Problem

Low-light images usually suffer from a mix of issues that are hard to fix with classic filters:

- noise amplification
- color shifts / white balance problems
- loss of detail in shadows
- varying exposure conditions across devices

The goal was a simple UX: “drop an image, get back a better version” without requiring users to tune parameters.

## First Attempt (and Why It Failed): Zero-DCE

I started with **Zero-DCE** because it’s lightweight and doesn’t require paired low/normal-light ground truth.

In practice, my implementation didn’t meet the bar for a deployable app:

- **Output instability** across different scenes (some images improved, others developed artifacts)
- **Hard-to-debug behavior** when trying to tune curves and preprocessing
- **Integration friction**: getting consistent results required more iteration than the project timeline allowed

Instead of forcing it, I treated this as an engineering decision: ship something reliable, then iterate.

## Pivot: Why MIRNet

I switched to a **pretrained MIRNet**-based approach because it gave me a stable baseline that was easier to productionize:

- **Predictable enhancement quality** without retraining from scratch
- **Cleaner inference pipeline** (standard normalization/denormalization, straightforward tensor handling)
- **Better end-to-end reliability** for a web workflow (upload → inference → return image)

This wasn’t “the best model possible” — it was the best choice for building a product-like system under constraints.

## System Design

### Backend (Flask + PyTorch)

- Loads the model once at startup (avoids cold-start penalties per request)
- Accepts an uploaded image, runs preprocessing + inference, returns an enhanced image
- Enforces basic safeguards (file type checks, size limits, predictable error responses)

### Frontend (React)

- File upload UX with clear states: idle → uploading → processing → done/error
- Before/after preview so the user can judge results immediately
- Download action that returns the processed output as an image file

## Challenges I Hit (Real-World)

- **Latency vs. quality**: larger models can look better but feel slower; I prioritized responsiveness for single-image requests.
- **Memory constraints**: high-resolution images can blow up RAM/VRAM; resizing and safe limits were necessary.
- **Image I/O quirks**: different formats, orientations, and color spaces require defensive handling.
- **Deployment reality**: model inference wants a server runtime; the UI can be static-ish, but inference needs proper hosting.

## Practical Trade-Offs

- Used a pretrained model to **reduce risk** and get a dependable baseline.
- Focused on **robustness and DX** (stable API contracts, predictable errors) rather than squeezing out marginal visual gains.
- Kept the interface minimal so the app is usable without ML knowledge.

## What I Learned

- Turning CV research ideas into a product is mostly about **systems**: I/O, failure modes, latency, and integration.
- “Works in a notebook” is not enough — **operational reliability** matters more than model novelty for most users.
- Pivoting quickly (Zero-DCE → MIRNet) is sometimes the most technical decision you can make.

## Next Improvements

- Batch uploads and background processing
- Optional user controls (strength, denoise level) with safe defaults
- Containerized deployment and a clearer separation between UI hosting and inference hosting
